# ToGo: бриф идеи приложения для разработки агента

## 1. Краткое описание

ToGo - мобильное веб-приложение/PWA для планирования отдыха вечером после
работы, на выходных, в короткой поездке или отпуске. Главная задача приложения -
быстро предложить пользователю реалистичные варианты отдыха с учетом времени,
домашней локации, бюджета, дороги, погоды, транспорта, жилья, еды и личных
предпочтений.

Приложение должно работать в браузере на телефоне как основной сценарий, но
также корректно открываться на компьютере.

## 2. Главная пользовательская проблема

У пользователя есть свободное время, но он не хочет вручную проверять десятки
сервисов:

- куда можно успеть съездить;
- сколько займет дорога;
- сколько будут стоить билеты;
- есть ли жилье;
- какая будет погода;
- что там делать;
- где поесть;
- получится ли уложиться в бюджет;
- что взять с собой.

ToGo должен собрать это в один понятный сценарий отдыха.

## 3. Основная идея агента

Агент должен быть не просто поисковиком мест, а планировщиком решения:

1. Понять ограничения пользователя.
2. Сгенерировать подходящие направления или активности.
3. Оценить логистику, бюджет и погоду.
4. Отранжировать варианты.
5. Объяснить, почему каждый вариант подходит или не подходит.
6. Сформировать готовый план: дорога, жилье, еда, места, чек-лист.

Агент должен отдавать не абстрактные советы, а конкретные карточки вариантов.

## 4. Основные режимы отдыха

### 4.1 Вечер после работы

Фокус:

- минимальная логистика;
- небольшая усталость пользователя;
- короткое время на дорогу;
- сценарии рядом с домом;
- бесплатные или недорогие активности;
- возможность отменить без потерь.

Примеры:

- прогулка у дома;
- парк;
- кофе;
- короткая поездка в центр;
- домашний вечер восстановления;
- кино, ужин, короткий маршрут.

### 4.2 Один выходной день

Фокус:

- поездка без ночевки;
- понятный маршрут туда-обратно;
- 1-3 ключевые активности;
- еда по пути;
- запас времени на дорогу обратно.

### 4.3 Два дня

Фокус:

- поездка с одной ночевкой;
- жилье;
- больше требований к чек-листу;
- прогноз погоды на оба дня;
- разумная дорога, чтобы поездка не превратилась только в транспорт.

### 4.4 Несколько дней или отпуск

Фокус:

- дальние направления;
- самолеты, поезда, автобусы;
- комбинации транспорта;
- варианты жилья;
- распределение активностей по дням;
- бюджет на весь период и на человека.

## 5. Домашняя локация и зона "рядом"

Пользователь должен иметь домашнюю локацию.

Пример:

- пользователь живет в Петергофе;
- рядом может считаться сам Петергоф;
- отдельно может быть Санкт-Петербург;
- отдельно - Гатчина, Пушкин, Павловск, Кронштадт;
- дальние поездки начинаются за пределами домашней зоны.

Настройки:

- город;
- район или точка дома;
- радиус "рядом с домом" в километрах;
- максимальное время дороги по умолчанию;
- транспорт по умолчанию;
- количество человек по умолчанию.

Важно: расстояние в километрах не должно быть единственным критерием. Для
пользователя важнее фактическое время в пути, пересадки, расписание и сложность
логистики.

## 6. Вводные параметры пользователя

Агент должен учитывать:

- сколько есть времени;
- даты поездки или период;
- город/регион, если пользователь знает направление;
- режим "не важно куда";
- хочет ли пользователь ехать далеко;
- максимальное время на дорогу;
- бюджет;
- бюджет общий или на человека;
- количество человек;
- допустимый транспорт;
- желание отдохнуть бесплатно;
- настроение отдыха:
  - спокойный;
  - активный;
  - культурный;
  - романтический;
  - семейный;
  - с друзьями;
  - гастрономический;
  - природа;
  - восстановление после работы.

## 7. Логика выбора направления

Должны быть два режима:

### 7.1 "Важно куда"

Пользователь выбирает:

- город;
- регион;
- конкретную точку;
- тип места.

Агент подбирает маршруты, жилье, еду, погоду и активности для выбранного места.

### 7.2 "Не важно куда"

Пользователь задает ограничения, а агент предлагает разные варианты.

Для каждого варианта нужно кратко показать:

- куда ехать;
- сколько ехать поездом;
- сколько лететь самолетом;
- есть ли автобус;
- сколько стоит дорога;
- сколько стоит жилье;
- какая погода;
- что посмотреть;
- почему вариант стоит рассмотреть.

## 8. Транспорт

Для ближних поездок:

- пешком;
- такси;
- личный автомобиль;
- автобус;
- электричка;
- метро;
- комбинированный городской маршрут.

Для дальних поездок:

- самолет;
- поезд;
- автобус;
- автомобиль;
- комбинированные маршруты с пересадками.

Для самолетов обязательно поддержать два отдельных сценария:

1. Вылет "из дома" или ближайшего аэропорта.
2. Вылет "из Москвы", если это может быть дешевле или удобнее.

Для каждого транспортного варианта:

- время в пути;
- цена на человека;
- цена на всех;
- пересадки;
- время выезда;
- время прибытия;
- дорога до вокзала/аэропорта;
- буфер на регистрацию, посадку и пересадки;
- источник данных.

## 9. Бюджет

Пользователь может указать:

- общий бюджет поездки;
- бюджет на человека;
- количество людей;
- нужно ли считать транспорт на всех или отдельно;
- нужен ли режим "бесплатно".

Агент должен оценивать минимум:

- дорогу;
- жилье;
- еду;
- билеты в музеи/парки/активности;
- локальный транспорт;
- запас на непредвиденные расходы.

Карточка должна ясно показывать:

- вписывается ли вариант в бюджет;
- насколько сильно превышает бюджет;
- какой самый дорогой компонент;
- можно ли удешевить вариант.

## 10. Режим "отдохнуть бесплатно"

Этот режим не означает "вообще без денег при любой дальности". Агент должен
разделять:

- бесплатные активности;
- бесплатный отдых рядом с домом;
- поездку, где активности бесплатные, но дорога платная.

Примеры бесплатного отдыха:

- прогулочные маршруты;
- парки;
- бесплатные музеи и дни бесплатного посещения;
- пикник;
- самостоятельная экскурсия;
- красивые места для фото;
- домашний вечер;
- события без входного билета.

## 11. Погода

Нужно показывать:

- погоду дома на момент выезда;
- погоду в месте посещения;
- температуру;
- ощущается как;
- осадки;
- ветер;
- вероятность дождя/снега;
- рекомендации по одежде.

Для поездок на несколько дней агент должен учитывать прогноз по дням, а не одну
температуру.

## 12. Места и активности

Для направления агент должен предлагать категории:

- достопримечательности;
- музеи;
- парки;
- прогулочные маршруты;
- смотровые площадки;
- природа;
- события;
- бесплатные места;
- необычные места;
- фототочки;
- места для детей;
- вечерние активности.

Каждая активность должна иметь:

- название;
- краткое описание;
- категорию;
- платно/бесплатно;
- примерное время посещения;
- район;
- почему подходит к выбранному сценарию.

## 13. Еда

Агент должен предлагать места, где поесть.

Фильтры:

- цена;
- расположение;
- кухня;
- рейтинг;
- завтрак;
- обед;
- ужин;
- быстрый перекус;
- романтический ужин;
- семейное место;
- локальная кухня.

Важно учитывать время поездки: для вечера после работы не нужно предлагать
сложный маршрут ради ресторана на другом конце города.

## 14. Жилье

Для поездок с ночевкой агент должен предлагать:

- квартиры;
- гостиницы;
- хостелы;
- апартаменты;
- загородные варианты.

Фильтры:

- цена;
- рейтинг;
- расстояние до центра или ключевых мест;
- тип жилья;
- количество гостей;
- отмена бронирования;
- удобство заезда.

Возможные источники:

- Avito;
- 101hotels;
- Ostrovok;
- Яндекс Путешествия;
- другие легальные API/партнерские источники.

Скрейпинг без разрешения не должен быть базовым подходом.

## 15. Чек-листы

Если это поездка, агент должен предлагать базовые чек-листы.

Стандартные шаблоны:

- минимум вещей;
- один рюкзак;
- максимум, что может понадобиться;
- поездка на один день;
- поездка с ночевкой;
- поездка летом;
- поездка зимой;
- холодная погода;
- документы и деньги;
- аптечка;
- электроника;
- еда и вода;
- поездка с детьми;
- поездка на машине.

Пользователь должен иметь возможность:

- отмечать пункты;
- добавлять пункты;
- удалять пункты;
- редактировать стандартные пункты;
- создавать свои чек-листы;
- сохранять чек-лист под конкретный план.

## 16. Формат карточки варианта

Карточка должна быть короткой, но информативной.

Минимальные поля:

- название;
- город/место;
- тип отдыха;
- расстояние от дома;
- время в пути;
- доступный транспорт;
- цена дороги;
- цена жилья;
- примерная общая стоимость;
- стоимость на человека;
- погода;
- 2-3 интересных места;
- 1-2 места, где поесть;
- подходит ли под бюджет;
- подходит ли под длительность;
- теги.

Примеры тегов:

- бесплатно;
- рядом;
- можно после работы;
- можно с детьми;
- романтично;
- спокойно;
- активно;
- природа;
- культура;
- еда;
- нужен самолет;
- без ночевки.

## 17. Детальный план

При открытии карточки агент должен показать:

1. Почему вариант подходит.
2. Примерный план по времени.
3. Как добраться.
4. Сколько стоит.
5. Где жить.
6. Где есть.
7. Что посмотреть.
8. Какая будет погода.
9. Что взять с собой.
10. Какие есть риски:
    - плохая погода;
    - дорогое жилье;
    - длинная дорога;
    - мало времени;
    - поздний обратный транспорт.

## 18. Ранжирование вариантов

Агент должен ранжировать варианты не только по цене.

Факторы:

- соответствие длительности;
- укладывается ли дорога в лимит;
- укладывается ли бюджет;
- усталость и сложность маршрута;
- погода;
- количество пересадок;
- доступность жилья;
- количество интересных мест;
- бесплатные опции;
- сезонность;
- личные предпочтения пользователя;
- насколько легко отменить план.

Для каждого варианта агент должен уметь объяснить скоринг простыми словами.

## 19. Источники данных

Будущие интеграции:

- погода;
- карты и маршруты;
- расписания поездов;
- авиабилеты;
- автобусы;
- жилье;
- рестораны;
- достопримечательности;
- события;
- бесплатные мероприятия;
- календарь пользователя.

Архитектурно каждый источник должен быть отдельным адаптером:

- `weatherProvider`;
- `transportProvider`;
- `accommodationProvider`;
- `foodProvider`;
- `placesProvider`;
- `eventsProvider`.

Агент не должен быть жестко привязан к одному сервису.

## 20. Хранение данных

На MVP-этапе достаточно локального хранения:

- настройки пользователя;
- домашняя локация;
- сохраненные планы;
- чек-листы;
- избранные направления.

Для PWA лучше использовать:

- localStorage для простых настроек;
- IndexedDB для более сложных данных;
- экспорт/импорт JSON для ручного бэкапа.

Если позже нужна синхронизация между устройствами, добавить аккаунт и серверное
хранение.

## 21. UX-принципы

Приложение должно быть mobile-first.

Важно:

- большие кнопки;
- быстрые фильтры-чипсы;
- нижняя навигация;
- минимум длинных форм;
- пошаговый подбор для сложных сценариев;
- понятные пустые состояния;
- объяснения, почему вариантов нет;
- темная тема;
- offline-friendly чек-листы и сохраненные планы.

Главный UX-принцип: пользователь не должен чувствовать, что он заполняет анкету.
Он должен ощущать, что приложение быстро сужает хаос до нескольких нормальных
вариантов.

## 22. MVP

Первый рабочий MVP:

- PWA;
- mobile-first интерфейс;
- домашняя локация;
- форма подбора;
- моковые направления;
- карточки вариантов;
- детальная страница;
- расчет примерной стоимости;
- погода моками;
- жилье моками;
- еда моками;
- интересные места моками;
- чек-листы;
- сохраненные планы;
- localStorage.

Главная цель MVP - проверить механику выбора и полезность карточек, а не сразу
подключить все внешние сервисы.

## 23. Следующие этапы

### Этап 2

- реальный API погоды;
- реальные карты;
- расчет времени маршрута;
- улучшение домашней зоны;
- экспорт/импорт планов.

### Этап 3

- билеты на поезда;
- авиабилеты;
- автобусы;
- жилье;
- фильтры по цене и району.

### Этап 4

- события;
- персонализация;
- история предпочтений;
- объяснимый скоринг;
- режим "сюрприз";
- календарь пользователя.

### Этап 5

- синхронизация между устройствами;
- аккаунт;
- совместное планирование с другим человеком;
- партнерские ссылки;
- уведомления.

## 24. Нефункциональные требования

- Быстрая загрузка на мобильной сети.
- Работа базовых функций офлайн.
- Доступность: контраст, большие цели нажатия, корректные labels.
- Безопасное хранение домашней локации.
- Явное управление приватностью.
- Легальная работа с внешними источниками данных.
- Код должен быть типизирован и разделен по слоям.
- UI не должен зависеть напрямую от конкретного API-провайдера.

## 25. Ключевой критерий качества

Хороший результат - когда пользователь за 30-60 секунд получает 3-7 понятных
вариантов отдыха и может сразу выбрать один из них без дополнительного
исследования в десяти вкладках.
